# OpenCode 2.0 source-store compatibility

[This firsthand report](https://github.com/anomalyco/opencode/issues/16077#issuecomment-5792331045) from the maintainer of [deja-vu](https://github.com/vshulcz/deja-vu) says that OpenCode **2.0.12** writes a different session schema. This is a migration warning, not a verified compatibility claim for this project: the reader here was built against the 1.x `session` / `message` / `part` tables, and the development host reported OpenCode 1.18.32 on 2026-09-23. Verify the exact 2.x schema and real rows on a disposable installation before changing the reader or advertising 2.x support.

## Reported changes and impact here

| Reported OpenCode 2.0 change | Current dependency / consequence |
| --- | --- |
| `session` becomes `session_v2` | `listSessions()` and `getSession()` in `src/reader.ts` query `session`; sync, source metadata, orphan pruning, and live reads cannot work unchanged. Confirm column names, archive semantics, and update timestamps before reusing the existing Zod row schema and watermark. |
| `message` and `part` become `session_message`; role is in a `type` column and an assistant turn's parts are inside its `data` blob | `getTranscript()`, `materializeMessages()`, `getTranscriptContext()`, and `transcriptHasMarker()` all query the old tables. A table rename alone is insufficient: ordering, IDs, anchor selection, bounded-window counts, and parsing must be adapted to the actual new rows. `src/parser.ts` still expects normalized user/assistant messages and text/tool parts. |
| Tool names `bash` → `shell`, `apply_patch` → `patch`; file identifier `filePath` → `path`; output `state.output` string → `state.content` blocks | This project's indexed exchanges currently keep **tool names**, not tool arguments or output. Searchability of tool-name terms can change, but `path` and `state.content` are not directly indexed by the current parser. The `episodic_read_window` / `episodic_read_session` renderers may expose more raw context after a reader migration; do not promise file-path or output search without a separate, privacy-reviewed indexing change. |

The first failure on a 2.x-only source is likely a SQLite `no such table` error, rather than a clean compatibility diagnostic. `syncAll()` should fail loudly when the source layout is unsupported; `session.idle` reindex catches and logs errors. An old local index can still contain earlier chunks, but it is not evidence that new sessions are being indexed. Live transcript/window reads also require the old tables. Do not solve this by swallowing the error, returning an empty session list, or pruning the index against an undetected schema: that could silently lose searchable history. The index schema itself is owned by this project and is not directly changed by OpenCode's table migration.

## Migration checks before implementation

1. Capture `sqlite_master`, `PRAGMA table_info` for the reported tables, and representative **redacted** user, assistant, text, tool, multi-part, archived, and updated-session rows from a 2.x fixture; check whether old and new tables can coexist during migration. Do not commit real transcripts. Confirm the comment's claims against those rows rather than guessing the shape of `data`.
2. Detect the source schema explicitly and route 1.x and 2.x through separate read-only adapters that produce the same `SourceSession` / `SourceMessage` contract. Reject unknown or partial layouts before sync or pruning. Keep structural drift fail-loud and per-blob degradation limited to known layouts.
3. Rebuild the **authoritative privacy gate** over every raw content-bearing blob in the 2.x layout before materializing, indexing, or serving live/cached context. Preserve the literal `DO NOT INDEX THIS CHAT` substring behavior even when JSON is malformed or the marker appears in a nested part. Test removal of the marker and current-source indexed-read denial too.
4. Prove stable message ordering and user-message anchors for `episodic_read_window`; verify bounded context and omission limits against nested parts, including oversized content. Preserve one SQLite snapshot for privacy check plus window reads.
5. Exercise 1.x and 2.x fixture-based `listSessions`, full reads, windows, incremental sync, deleted-session pruning, and unsupported-schema failures. On upgrade, reindex changed transcript representations deliberately; a reused `session.time_updated` watermark may leave old chunks and anchors untouched even if the source schema changed. Validate the CLI and plugin harness on a real 2.x installation before claiming support.

## Retrieval semantics, independent of schema

The commenter also points out that dated, session-linked transcript hits let a reader inspect an older decision alongside a later reversal. This project already returns dates, titles, source IDs where applicable, and message anchors/windows; it does **not** maintain a temporal fact ledger or automatically supersede obsolete advice. The recall skill tells the agent to distinguish decisions from abandoned attempts, but a later hit is evidence to investigate, not proof that it remains current. Likewise, the comment's useful signal of a command that worked after a failed one is **not available to indexed search here** because tool output is deliberately omitted. An agent can inspect live context when available, subject to the privacy gate and bounded-window limits; foreign-source indexed excerpts cannot recover omitted output. Keep those limitations explicit rather than treating transcript provenance as state invalidation.

The comment also describes deja-vu's separate multi-harness MCP index. That is an architectural alternative, not an OpenCode 2.0 migration requirement for this OpenCode-only native plugin. A cross-harness MCP rewrite would be a separate product decision.
